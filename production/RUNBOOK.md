# Overnight production runbook

This is what a scheduled Claude session (a *shift*) does, every hour overnight,
until `production/queue.json` is finished. It works through the queue in order,
one task at a time, saving after every step so nothing is lost if the shift
stops (for example when Claude usage runs out: the next shift after the usage
limit resets picks up where this one stopped).

You are the showrunner's crew: map builder, prop sourcer, and, for episodes,
every Claude step of the pipeline (planner, writer, continuity editor, wiki
editor, packager). The rules engine still rolls every die. Quality matters
more than speed: a task done well and saved is worth more than three rushed.

## How your work reaches GitHub (read this first)

Shifts **cannot push** to the repository. You clone it read-only and work on
your local copy as normal. To save, you **pack** what you changed into a text
*bundle* and **upload it to Google Drive**; a GitHub Action
(`.github/workflows/relay.yml`) applies new bundles every 10 minutes: it checks
every file's hash, regenerates the derived files (maps from their generators,
episodes from their fixtures, the wiki), runs the tests, commits and pushes, and
starts the wiki and video-release workflows. `production/applied.json` in the
repository records every bundle it applied or rejected (with the reason).

* Drive folder id: given in your instructions (the scheduled task's prompt). It is deliberately
  not stored in this public repository; export it as `PQC_DRIVE_FOLDER` before packing.
* Pack: `python3 scripts/relay.py pack "<message>"` prints one or more bundle
  names and the exact `create_file` call to make for each.
* Upload each bundle, in the printed order, with the Google Drive `create_file`
  tool (load it with ToolSearch `select:mcp__Google_Drive__create_file`):
  `title` = `<name>.txt`, `parentId` = the folder id, `contentMimeType` =
  `text/plain`, `disableConversionToGoogleType` = `true`, `textContent` = the
  bundle **exactly** as `cat .relay/out/<name>.txt` prints it. Every file in it is
  hash-checked; a bundle copied inexactly is rejected, not half-applied.
* Only text you write travels: fixtures, scripts (including map generators),
  `assets/manifest.json`, map JSON, `production/queue.json` and `LOG.md`,
  `pqc/`, `prompts/`, `schemas/`, `tests/`, `campaign/`, `wiki/data/`,
  `bible/RETCONS.md`, `README.md`, and small images under `assets/sprites/`
  (24 KB max). Everything else (`state/`, `episodes/`, `wiki/docs/`, previews)
  is regenerated by the Action from those. Never upload anything else to the
  folder besides bundles and the shift markers below.

## 0. Setup (every shift)

```bash
git clone --depth 50 https://github.com/Nat20-Pixel-Saga/Nat20-Pixel-Saga /home/claude/nat20
cd /home/claude/nat20
export PQC_DRIVE_FOLDER=<the Drive folder id from your instructions>
git config user.name "pqc-shift"; git config user.email "pqc-shift@users.noreply.github.com"
scripts/fetch_assets.sh                          # CC0 art/audio + fonts into vendor/ (not in git)
python3 -m unittest discover -s tests -q         # must pass before you start (about 40 s)
SESSION="shift-$(date -u +%Y%m%d-%H%M)"
python3 scripts/relay.py begin "$SESSION"
```

Then, with the Drive `search_files` tool (`excludeContentSnippets: true`,
`pageSize: 1000`):

1. **Is another shift working?** Query `parentId = '<folder id>'
   and createdTime > '<now minus 75 minutes, RFC 3339 UTC>'`. If any title is a
   bundle or a `shift-start-…` marker of **another** shift (session names start
   with `shift-`) and that session has no `shift-end-<session>.txt`, it is still
   working: stop quietly. Bundles from sessions not named `shift-…` (setup and
   test sessions run by hand) never count as a running shift.
2. **Is the repository up to date?** Query `parentId = '<folder id>'`,
   write all titles to `/tmp/names.txt` (one per line), and run
   `python3 scripts/relay.py pending /tmp/names.txt`. If it lists bundles still
   waiting, the Action hasn't applied them yet: wait 10 minutes, `git pull`, and
   check again (up to three times); if they are still waiting, stop.
3. **Did anything get rejected?** Look at `production/applied.json` for entries
   with `"status": "rejected"` since the last shift. Their changes are not in the
   repository: read the reason, and redo that work first (the queue still shows it
   as not done).
4. Upload the marker `shift-start-<SESSION>.txt` (text/plain, content: the session
   name and the UTC time) to the folder.

If the tests fail on a clean checkout, do not start a task: fix the cause if it
is small and obvious (and pack it), otherwise log what is broken, pack, upload,
and stop.

## 1. The loop

```bash
python3 scripts/production.py next     # prints the next task as JSON; exit 2 = nothing ready
python3 scripts/production.py start <id>
# ... do the task (sections 2-4) ...
python3 scripts/production.py done <id> "<one-line note>"
python3 scripts/production.py log "<what you did, problems, timings>"
python3 scripts/relay.py pack "<id>: <summary>"      # then upload what it prints
```

* After **every** finished task and after every authored episode step, pack and
  upload (work in progress is fine: `wip(episode:2): plan`).
* If a task cannot be done well (missing art the pack doesn't have, a rules gap),
  `production.py block <id> "<reason>"`, log it, pack, upload, and continue with
  the next ready task. Never fake a result.
* When `next` exits with 2 and every task is `done` (or `blocked`), finish (section 5).

## 2. Map tasks (`map:<id>`)

1. Read the task `spec`, the campaign beats of the episodes in `for`
   (`campaign/c01.json`) and the location in `bible/03_gazetteer.md`.
2. Look at the pack's tilesets to pick tiles: `python3 scripts/tileset_atlas.py
   Backgrounds/Tilesets/<Sheet>.png /tmp/atlas.png` and Read the PNG. Useful sheets:
   TilesetNature (trees, rocks, logs), TilesetElement (carts, crates, hay, signs, furniture),
   TilesetFloorDetail (tracks, bones, cracks), TilesetWater, TilesetField,
   TilesetTowers, TilesetVillageAbandoned, tileset_camp, TilesetHouse, Interior/*.
3. Add any new props/terrain to `assets/manifest.json` (`rect` in tiles, `solid`:
   all/base/none, `light` for light sources). Keep ids lowercase_with_underscores.
4. Write a generator `scripts/maps/<id>.py` (follow `scripts/maps/lantern_road.py`)
   that writes `assets/maps/<id>.json`: base terrain, autotiled layers, props, and
   **named points for every mark the episodes will need** (scene centres, fight
   areas, entrances). Points must be free squares (a test checks this).
5. `python3 scripts/map_preview.py <id> /tmp/<id>.png --points`, Read the PNG,
   and iterate until it reads clearly at a glance: paths connect, nothing
   important is hidden behind canopy, fight areas are open (at least 10x8 free
   squares), the map edges look natural.
6. `cd tests && python3 -m unittest test_render` must pass. Pack and upload
   (the Action re-runs the generator and writes the preview).

## 3. Materials tasks (`materials:<id>`)

Find each item in the pack (`vendor/ninja-adventure/`: `Actor/Character`,
`Actor/Animal`, `Actor/Monster`, `Backgrounds/Animated`, `FX`, `Items`), add it
to the manifest (actors: `src` folder, optional `recolor`, `voice`; props as
above), and check it loads (`tests/test_render`). If something truly does not
exist, use the closest stand-in, mark it `"stand_in": true` with a `note`, and
add a row to "Materials still wanted" in the README so the showrunner can source
it. A sprite you draw yourself goes under `assets/sprites/` (manifest paths that
start with `assets/` load from the repository; keep each PNG under 24 KB). Pack
and upload.

## 4. Episode tasks (`episode:<n>`)

The pipeline runs in **agent mode**: whenever it needs a Claude step, it writes
the exact prompt the API would receive to `episodes/<id>/pending/<step>.md` and
exits with code 3. You write the answer as JSON to `fixtures/<id>/<step>.json`
and run it again.

```bash
python3 scripts/run_episode.py <n> --agent ; echo "exit $?"
```

Repeat until it exits 0. For each pending step:

1. **Read the whole pending prompt.** For DM steps (plan, script, continuity),
   also read what it lists: `bible/00`, `01`, `06`, `08`, `10`, `RETCONS.md`
   and the four dossiers. For PUBLIC steps (wiki_facts, packaging) do **not**
   open the bible or dossiers: use only the prompt, so nothing secret leaks.
2. Use the Episode 1 fixtures (`fixtures/C01-E001/*.json`) as the model of
   shape and quality.
3. Write the JSON exactly to the schema, run again, then pack and upload
   (`wip(episode:<n>): <step>`), so a later shift can resume from it.

Step notes:

* **plan**: honour the campaign beat and key rolls. Use only points/squares on
  the maps; check positions with `python3 scripts/map_preview.py <map> /tmp/m.png
  --points --blocked`. Validation problems come back in the next pending prompt.
* **script**: write *after* reading the outcomes in the prompt (the dice are
  final; a failure is a failure). 35-55 boxes, the run prints the runtime: aim
  for 6-9 minutes, never outside 5-10 (rewrite if it is). Every voice per its
  dossier; the last box is a party member's; no numbers in narration after a roll.
* **continuity**: be the honest editor of your own script: re-read it against
  the outcomes, the dossiers and the SECRET blocks. A blocker sends it back;
  that is the point. Do not mark `ok` if you found a real contradiction.
* **wiki_facts** and **packaging**: only what was on screen. Quotes copied exactly.

When it exits 0, review before committing:

```bash
python3 scripts/contact_sheet.py <n>      # Read episodes/<id>/contact_sheet.png
```

Look for: speakers off screen, actors standing inside props, dice trays covering
the action, a scene that is too dark. Fix by editing the script fixture (or the
plan's marks, then everything after it: delete the later fixtures) and re-run.

Then commit the episode **locally** (so your next episode starts from it) and
tell the Action to do the same:

```bash
python3 scripts/run_episode.py <n> --agent --commit
python3 scripts/production.py done episode:<n> "<title>, <minutes> min"
python3 scripts/relay.py pack "Episode <n>: <title>" --episode-commit <n>   # then upload
```

The Action replays the episode from your fixtures (the dice are seeded, so the
result is identical), commits it, rebuilds the wiki, and
`.github/workflows/release.yml` renders the 1080p video and publishes it as a
release tagged with the episode id. Sessions cannot create releases; don't try.

`--commit` advances `state/` and rebuilds `wiki/docs/`; it refuses to run if the
state is not exactly at the previous episode, which protects the order. Never
re-roll: if an episode's dice give a bad night for the party, that is the story.
A technical failure that forces a re-run uses `--attempt 2` and an
`attempt_reasons` entry (bible 10 §2).

## 5. Finishing

Before the shift ends for any reason (queue done, time, usage running low):
pack and upload whatever is finished, then upload `shift-end-<SESSION>.txt`.

When nothing is left in the queue: write a short summary at the top of
`production/LOG.md` (episodes produced with runtimes, maps built, anything
blocked and why), pack and upload it, upload the shift-end marker, then turn off
the schedule: use the scheduled-task tools (`list_triggers`, then
`update_trigger` with `enabled: false`) on the task named **"Nat 20 Pixels
overnight production"**. Never turn it off for any other reason.
